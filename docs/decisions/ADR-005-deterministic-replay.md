# ADR-005: Deterministic level seeds with server-side replay validation

- **Status:** Accepted
- **Date:** 2026-05-25

## Context

Scores drive a competitive leaderboard, so the server must not trust a score sent by
the client. The classic options are (a) run the game on the server and stream state to
the client, (b) trust the client and detect cheating statistically after the fact, or
(c) make the game deterministic, let the client play, and have the server re-derive the
result from the inputs.

A match-3-style puzzle has a small input space (a list of chains) and a small state
space (a 7×7 grid), and the board's randomness is the only non-determinism.

## Decision

- The board is generated from a 32-bit seed with a fixed PRNG (mulberry32) and a fully
  specified draw order (`docs/engine.md`). Seed and config come from the event; the
  server hands them out at `POST /v1/heists/start`.
- The server stores only `{runId, playerId, eventId, seed, configVersion, boosters,
  status, timestamps}` — never a board.
- On `finish`, the client submits its moves and its computed score. The server replays
  the moves through the Go engine against the pinned config, rejects any illegal move
  (`INVALID_REPLAY`), rejects any score that differs from the replay (`SCORE_MISMATCH`),
  and applies plausibility bounds on duration and move count (`IMPLAUSIBLE_RESULT`).
  Only the server's score reaches the leaderboard.
- The engine exists twice (Go, TypeScript). A golden fixture file generated by Go and
  asserted by Vitest guarantees identical boards, loot and scores for identical inputs.

## Consequences

Positive:

- A forged score is impossible: the score is a function of the moves, and the moves are
  validated. Injecting an illegal chain, skipping a lock, or claiming extra moves fails
  deterministically.
- Storage per run is a few hundred bytes regardless of run length; there is no board
  state to persist, version or migrate.
- Replays are cheap to store and useful beyond validation: support can reproduce any run,
  and they are the ground truth for balancing analytics.
- The client is fully offline-capable during a run; the server is involved only at
  start and finish, which keeps request volume low and latency irrelevant to gameplay.
- Determinism made the engine straightforward to test exhaustively in both languages.

Negative:

- It does not stop a *perfect* player. Because the board is deterministic and the seed is
  revealed at start, a bot can search for the optimal chain sequence and submit a legal,
  plausible, superhuman replay. The plausibility bounds (minimum 120 ms per move, move
  caps) raise the cost; they do not eliminate it. Real mitigation is statistical
  (outlier detection on score distribution and timing) and is future work. I consider
  this the honest limit of the approach: it removes cheap cheating, not determined cheating.
- Two engine implementations must stay byte-identical. Every engine change is a
  two-codebase change plus regenerated fixtures. The CI golden test makes drift loud, but
  the maintenance cost is permanent.
- Floating point is banned in the engine (integer arithmetic only, `Math.imul` and `>>> 0`
  in JS) to keep cross-language determinism, which constrains how scoring formulas can be
  written.
- Replay costs CPU on the server proportional to move count. The plausibility caps bound
  it, and a replay is microseconds for a normal run, but it is the one CPU-heavy step in
  an otherwise I/O-bound API and is why the API autoscales on CPU as well as requests.

## Alternatives considered

- **Server-authoritative simulation** — every move is a request. Latency becomes part of
  the feel of a casual puzzle, request volume rises by two orders of magnitude, and
  offline play disappears. Rejected.
- **Trust the client, flag outliers later** — cheap and common in casual games, but the
  leaderboard would show forged scores until a batch job removed them, and "removed
  after the fact" is a poor story for the competitive loop this game is built around.
  Rejected as the primary mechanism; kept as a planned complement.
- **Signed client state / attestation** — depends on the client being tamper-resistant,
  which a web client is not. Rejected.
- **Hidden seed, revealed only at finish** — would defeat pre-computation bots, but the
  client needs the seed to generate the board. Could be replaced by a server-generated
  board sent at start, at the cost of the "no board storage" property. Not chosen for the MVP.
