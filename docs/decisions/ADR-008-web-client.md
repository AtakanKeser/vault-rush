# ADR-008: HTML5 Canvas web client for the MVP instead of Unity

- **Status:** Accepted
- **Date:** 2026-08-30

## Context

The game is designed as a mobile title, and Unity would be the conventional client. But
this project is a backend portfolio: the client exists to exercise the API end to end,
to prove the deterministic engine works in a second language, and to give reviewers
something they can open in a browser in ten seconds. Whatever client I build must run in
CI, because the cross-language golden test (ADR-005) is the safety net for the engine.

I am one person with limited time; the client must not consume the schedule the backend
needs.

## Decision

The MVP client is a Vite + TypeScript application rendering to an HTML5 Canvas, served
as static files (S3 + CloudFront in production, nginx in compose). The TypeScript engine
in `client/src/engine` is the second implementation of `docs/engine.md` and is tested
with Vitest against fixtures generated by the Go engine.

A Unity client is a planned follow-up. It will consume the same HTTP API and the same
engine specification; nothing in the backend is web-specific.

## Consequences

Positive:

- The engine's determinism is verified in CI on every push (`client` job: typecheck,
  Vitest, build). With Unity I would need licensed build agents or manual test runs,
  and the golden test would lose most of its value.
- Zero install for reviewers: a URL. That matters more for a portfolio than a store
  listing.
- Fast iteration: seconds from code change to a playable board, no editor, no import
  pipeline. The client took a fraction of the time the backend took, which is the ratio
  I wanted.
- One toolchain (Node) shared with the admin dashboard, one Dockerfile pattern, one
  deployment path (static to S3).
- A browser client is the harshest anti-cheat test environment — everything is
  inspectable — which forced the server-side replay design rather than allowing me to
  lean on client obfuscation.

Negative:

- It is not a mobile app. No store presence, no push notifications, no native haptics
  or IAP; touch handling on mobile browsers is workable but not native quality. A
  reviewer evaluating it as a *game* will find it modest. That is a conscious trade.
- The Unity follow-up means a third engine implementation (C#), with the same
  byte-for-byte determinism burden (ADR-005). The fixture file makes that tractable but
  not free. I chose the TypeScript client knowing this.
- Canvas rendering and game-feel work (animations, tweens, sound) are hand-rolled
  instead of engine-provided. I kept them minimal.
- The bearer token lives in browser storage, which is fine for a device-bound casual
  game identity with no password, but would need revisiting before adding accounts or
  payments.

## Alternatives considered

- **Unity from the start** — the "correct" mobile choice. Rejected for CI cost, iteration
  speed and the mismatch with the project's goal; explicitly deferred, not dismissed.
- **Godot** — open source, exports to web, GDScript or C#. A reasonable middle ground,
  but web exports are large and slow to load, and it would still be a third language for
  the engine. Rejected for the MVP.
- **Phaser / PixiJS** — would give me a scene graph and tweening for free on top of
  Canvas/WebGL. Reasonable; I chose plain Canvas because the board is a 7×7 grid and the
  rendering code is small enough that a framework would be more to learn than to write.
- **React Native / Flutter** — closer to mobile, but neither is a game framework and
  both add native build complexity to CI. Rejected.
- **No client, API-only with a bot** — the deterministic engine makes a headless bot
  possible, and one is planned for load testing. But a backend portfolio that nobody can
  *play* undersells the work. Rejected as the sole client.
